## 八、P0/P1 真机闭环（本轮补充，全部实机取证）

### 8.1 真因：Bank handle 跨帧缓存

P0-A "时好时坏" 的真因不是 PollLoop 顺序，而是内核把 Bank handle 缓存在 Galaxy 全局：

```galaxy
// 错误写法（懒加载）
void libVibeKernel_gf_EnsureBankLoaded() {
    if (libVibeKernel_gv_bankHandle == null) {          // <-- 只在 null 时 load
        libVibeKernel_gv_bankHandle = BankLoad(name, player);
    }
}
```

`gv_bankHandle` 的首次赋值发生在 `InitMap()` 的**第 2 条指令**（整局最早，InitLibs 都没跑）。
那一刻拿到的 handle 若不可用，判空此后恒为假、永不重试，
**整局所有 `BankValueSet*` / `BankSave` 静默 no-op**——不报错、不写日志、静态 lint 也查不出。

铁证：`InitMap()` 头两句紧挨着，`LibMapModBridge`（每次调用都重新 `BankLoad`）写
`CMRERebornDebug` 的 `stage16_before_vibe` / `stage16_after_vibe` 双双成功；
内核写 `GalaxyVibe` 的同名 index 键一个都没有。同帧、同时刻、同样是 Load+Set+Save，
唯一差别就是缓不缓存 handle。

修法：每次无条件 `BankLoad`。`BankLoad` 对已加载的 bank 返回引擎侧同一对象、不重读磁盘，
所以"连续写多个 key 会丢内存中未 Save 的键"这个顾虑不成立；真正碰磁盘的是 `BankReload`，
只保留在下行读取路径 `ReloadBank()` 里。

### 8.2 配套第二因：Host 非原子写

`write_bank_request` 原用 `tree.write(bank_path)`——就地截断再写。
内核每 0.5s 一次 `BankReload` 会撞上截断窗口，解析到半截 XML 得空 Bank，
随后内核自己 `BankSave` 把空内存态刷回磁盘，覆盖掉 host 刚写的请求。
改为写 `.tmp` + `os.replace` 原子覆盖。
