配置 3v2 / 3 episodes / max-steps 30：

```
ep1: 20 步 victory  R=+7.21   own 3→1   enemy 2→1→0
```

- 敌方单位数在 trace 里**逐步真实下降**（2→1→0），己方也有真实伤亡（3→2/3→1）——
  不是"跑满就判赢"。
- 终端 reward 明显跳变（+9.6~10.3），与过程 reward（−0.3~+0.9）量级分离。

### 2.2 反向对照复现：`--no-alliances`（`ppo-negctl-0310.json`）

> 同样是对前序 `run05_negctl` 的独立复现。

```
terminated = 0/2    wins = 0   episode_errors = 0
ep0: 30 步 未终止  R=-1.44   own 3→3   enemy 2→2   all_ok=True
ep1: 30 步 未终止  R=-1.42   own 3→3   enemy 2→2   all_ok=True
```

**这是教科书级反向对照**：不建交 → 打不动人 → 双方数量纹丝不动 → 没有终端。
但**动作全部执行成功（all_ok=True）、无 episode error、训练照常跑**。
失败精确落在被测判据（`terminated` / `wins`）上，而不是靠崩溃或超时。
→ 排掉「victory 是空判定 / 终端逻辑恒真」的假阳性。

### 2.3 难度旋钮标定：3v6 劣势局（`ppo-hard-3v6-0310.json`）

```
ep0: 19 步 defeat  R=-11.73   own 3→0   enemy 6→3（杀 3）
ep1: 13 步 defeat  R=-12.46   own 3→0   enemy 6→5（杀 1）
ep2: 19 步 defeat  R=-11.58   own 3→0   enemy 6→4（杀 2）
```

三点收获：
1. **终端是双向的**——不只会判 victory，defeat 同样触发。
2. **难度旋钮有效**：3v2=100% 胜 ↔ 3v6=100% 负，中间必然存在有区分度的配比。
3. **负局内部仍有 reward 梯度**（杀 2 的 −11.58 > 杀 1 的 −12.46），不是一刀切常数。

### 2.4 诚实标注：现在还**不能**说"策略学会了"

- 3v2 的 100% 胜率是**退化到平凡解**的经典形态——任务太简单，任何策略都能赢，
  单一"胜率"指标此时**不具备区分能力**。
- entropy 2.384 vs 最大熵 ln(19)=2.944 → 有效动作数约 10.8/19，策略确实在收缩，
  但**全程只发生了 1 次 PPO 更新**，收缩无法归因（可能来自 BC 初始化）。
- 结论口径：本轮证明的是**机制通了**（终端信号真实、双向、有梯度），
  **不是**"PPO 学到了东西"。后者需要 §4 的 learning curve。

### 2.5 3v6 run 被截断 —— 根因已查明：SC2 进程被重启

现象：报告只落了 3 个 episode（请求 4 个），汇总字段（`terminated_episodes`/`wins`/`losses`）
为 `null`，shell 退出码 127，stdout 日志 0 字节。按铁律"退出码与产物冲突时信产物"采信 JSON。

**根因（时间线对齐）**：

```
03:07:45  SC2 PID 36916 启动，:5000 LISTEN
03:32:11  本会话 3v6 run（pid 37348）取得 live 锁，开始跑
03:32:17  并行会话的 run06_longtrain 尝试启动 → 被锁挡下（live_lock_busy，见 §4.5）
03:33     3v6 报告落盘 3 个 episode，第 4 个断链，汇总字段 null
03:37:36  SC2 以**新 PID 33828** 启动 ←── 36916 已不在
```

即：**不是代码 bug，是 SC2 进程在 run 中途被重启**，WebSocket 断链导致第 4 个 episode
失败、汇总统计没走到。

**由此暴露出锁的能力边界（本轮最有价值的一条洞见）**：

> `live_lock` 保护的是"谁在用 :5000 / Bank"这一层。但一个**被锁挡住的会话**
> 完全可能转头去**重启 SC2 进程**（用户此前给过"真机线被阻塞时允许直接重启游戏"的授权），
> 这会照样打断持锁者。**锁挡住了并发访问，挡不住并发的环境重置。**

修法（已列入下一轮）：把"重启 SC2"这个动作也纳入锁的管辖——重启前必须先
`read_lock("sc2-port-5000")`，若持有者进程仍活着则**禁止重启**，改为等待或报错退出。
锁文件里已经存了 holder/pid/argv/note，信息是够的，缺的是"重启路径去查它"。

## 4. 新增基础设施：SC2 真机资源互斥锁

### 4.1 为什么做

本轮开工时扫环境发现：另一个会话的 PPO 训练（PID 3740）正占着 :5000。
进一步查，仓库里 **13 个真机入口默认全抢 `:5000`**，且共用同一个
`GalaxyVibe.SC2Bank`，**没有任何互斥机制**——完全靠人肉避让。

这正是本项目反复吃亏的模式：**纪律写在报告里，但没有一个进程在守它**
（对照 round24 的 `check_artifact_freshness.py` 教训）。纪律有半衰期，检查没有。

### 4.2 做了什么

`tools/galaxy-vibe/live_lock.py`：

- 锁文件放系统临时目录（`SC2_LIVE_LOCK_DIR` 可覆盖）→ **跨会话、跨进程、跨仓库副本**都能互斥。
- `os.open(O_CREAT|O_EXCL)` 原子创建；锁内记 holder / pid / token / acquired_at / note。
- **只删自己的锁**（release 时比对 token）——避免"回收了别人刚建的锁"。
- 过期回收保守：仅当持有者 PID 已死、或超硬上限（默认 1800s）才回收。
- `pid_alive()` 在 Windows 走 ctypes `OpenProcess`+`GetExitCodeProcess`，
  **绝不用 `os.kill(pid, 0)`**（Windows 上那是 TerminateProcess，会真杀进程）。
- 统一接入 helper：`add_lock_args(parser)` + `acquire_from_args(args, holder)`，
  各入口两行接入，退出码统一约定 **exit=3 = live_lock_busy**。
- CLI：`python live_lock.py status|clear [resource]`。

### 4.3 已接入的入口

`tier100_live_probe.py` / `route_b_rl_probe.py` / `real_machine_vm_live.py` /
`train_route_b.py`（本轮 4 个真机 run 全部带锁跑完，无冲突）。

### 4.4 判据自身的验证（防止"恒绿的锁"）

| 验证 | 结果 |
|---|---|
| 单测 `test_live_lock.py` | **16 passed**（原 11 条互斥/归属/回收 + 新增 5 条 `TestEnvDrift`，见 §4.6） |
| 变异检验 `mutation_check_live_lock.py` | **PASS** —— M1 互斥失效、M2 过度回收、M3 归属失校 三个变异体**全部被判据抓住** |
| 端到端接入验证 `verify_tier100_lock.py` | **PASS** —— 占锁时 tier100 exit=3/`live_lock_busy` 且报出持有者；释放后 exit=2/`connect=false`（走到网络层才失败）。**两种失败原因不同**，证明拦截确实来自锁而非网络 |

### 4.5 生产实证：本轮当场拦下一次真实并发

锁上线**二十分钟内就用上了**。03:32:11 本会话 3v6 run（pid 37348）持锁，
6 秒后并行会话的 `run06_longtrain` 启动，被干净拦下：

```json
{ "error": "live_lock_busy",
  "holder": { "holder": "train_route_b", "pid": 37348, "port": 5000,
              "argv": ["...train_route_b.py","--port","5000","--episodes","4",...],
              "note": "episodes=4", "acquired_at_iso": "2026-08-10T03:32:11" } }
```

```
[live-lock] SC2 真机资源 sc2-port-5000 被 train_route_b(pid=37348) 持有 6s；
            本次 holder=train_route_b。等待请加 --lock-timeout，强制请先确认对方确实已死。
```

若没有这把锁，两个 PPO 训练会同时抢 SC2 + **同一个 `GalaxyVibe.SC2Bank`**，
双方的观测/动作会互相污染，而且**大概率不会崩**——只会安静地产出两份错误数据。
这是最坏的一种失败：全绿、有报告、结论是假的。

（注意这仍未阻止 §2.5 的截断——原因见那一节，锁管不到"重启 SC2"。）

### 4.6 收尾增量：`env_drift()` —— 让被打断者"知情"（§2.5 的第一步）

§2.5 的完整治本是"重启 SC2 前先查锁"（拦在**动作发起方**，列入 §6.0）。但那要求所有
重启路径都改造，跨会话/跨工具，一轮做不完。本轮先做**成本最低、收益最确定**的一半：
让**被打断的一方**能明确知道自己被打断了，而不是安静地产出一份半截报告。

`live_lock.py` 新增：

- `sc2_pid_on_port(port)`：`netstat -ano -p TCP` 探 :5000 的 LISTEN 进程 PID（探不到返回
  `None`，宁可不判也不误判）。
- `LiveLock.acquire()` 时给 `sc2_pid_at_acquire` 拍一张快照（写进锁 payload，schemaVersion→2）。
- `LiveLock.env_drift()`：release 前对比"取锁时的 SC2 PID"与"现在的 SC2 PID"，
  返回 `sc2_restarted`（PID 变了）/ `sc2_gone`（端口没了且原进程已死）/ `None`（无漂移）。

接入 `train_route_b.py`：`finally` 释放锁前调用 `env_drift()`，若有漂移就把结果写进
`report["env_drift"]` 并打印 WARNING。这样 §2.5 那种"SC2 中途被换 PID"的 run，
**报告里会自带一条 `env_drift.kind=sc2_restarted`**，而不是留下一堆 null 让人事后猜。

判据自身的验证（防恒红/恒绿，`TestEnvDrift` test_12~16）：

| 测试 | 防的坏死形态 |
|---|---|
| test_12 无漂移必须返回 `None` | 防"恒红"——不能没事也报漂移 |
| test_13 PID 变化必须报 `sc2_restarted` | 正向能力 |
| test_14 无基线（取锁时探不到）不报 | 不拿缺失数据硬判 |
| test_15 `sc2_gone` 仅当持有者进程也死了才报 | 区分"SC2 没了"和"只是没在这个端口" |
| test_16 真实探测一个死端口必返回 `None` | 防探测器自身恒真 |

> 定位：这是**检测层**（被动知情），不是**预防层**（主动拦截）。预防仍是 §6.0，
> 最高优先。但有了检测层，即便预防没上，被污染的数据也不会伪装成干净数据蒙混过关。

## 6. 下一轮推进建议（按性价比排序）

0. **[基础设施·最高] 把"重启 SC2"纳入锁管辖的预防层**（§2.5）。本轮已补上**检测层**
   （§4.6 `env_drift`，被打断者会在报告里看到 `sc2_restarted`），但**预防层**仍缺：
   重启动作发起前须 `read_lock` 且持有者活着就禁止重启。当前状态下任何一次长训练
   仍可能被另一个会话的重启打断——区别只是现在**被打断的一方能知情**了，
   打断的一方仍不受约束。
1. **[模块②·高] 二分难度找区分带**：在 3v2（100% 胜）和 3v6（100% 负）之间扫
   3v3 / 3v4 / 3v5，找胜率落在 30~70% 的配比。这是能测出"学没学会"的**唯一前提**——
   在平凡解区间上跑 learning curve 等于自欺。
2. **[模块②·高] 在区分带上跑真 learning curve**：≥30 episodes，比较
   随机策略 / BC 初始化 / PPO 训练后 三条基线的胜率与熵轨迹。
   注意：n 小的时候胜率的置信区间极宽，30 局的 50%±18pp，**别把噪声当趋势**。
3. **[模块②·中] 修 §2.5 的 episode 截断 + 汇总字段 null**，并补一条单测钉住
   "报告的汇总字段与 episodes 列表必须自洽"。
4. **[基础设施·中] 把反向对照 `--no-alliances` 钉进 CI**：正向 PASS 若不配反向 FAIL，
   随时可能悄悄退化成恒绿。
5. **[模块①·中] G4-regression**（P0/P1 REPL + vibe gate G1-G8）可在现有真机窗口做；
   **G3-live-3500**（亡者之夜 3500 loop）需要 Ares launcher 独占 SC2 较久，建议单独排期。
