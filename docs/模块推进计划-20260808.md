## 依赖与排序

### 共同前置：可复现的运行时证据窗口

这不是把所有模块串行化的全局阻塞器，但 CMRE Stage 26、Neuro Stage 07、RL Stage 10
都需要一个受控的 SC2 运行窗口。每次 live 验证必须：

1. 只经 `tools/launchers/` 的批准 launcher 启动，不直接运行 `SC2_x64.exe`。
2. 使用新 run id 和端口，并确认 runtime lease 的归属；不得终止外部 owner。
3. 记录 launcher ready、CreateGame/JoinGame、推进帧、当前断言和同窗口 ScriptError
   verdict。
4. 把输入、命令、输出和异常放入对应模块的 `artifacts/` run 目录。
5. 对工作树中尚未验证的改动先运行范围内回归，再更新阶段 `result.json`。

**共同验收**：每个声称为 `runtime` 的结果都必须同时有 launcher/API 证据和本次窗口的
ScriptError verdict。launcher 退出码、进程启动、静态打包或浏览器回放不能代替该证据。

## 跨模块验证与状态更新

1. 每个模块在修改实现前先锁定当前结果中的通过断言，补齐缺失的回归测试后再变更行为。
2. 每次 run 使用新的 artifact 目录，包含命令、输入 hash、launcher 输出、断言、GameLogs
   verdict 和汇总结论。
3. 动态 run 后先验证输出是否属于当前 run window，再更新 `log.md`、`result.json` 和
   `issues.json`；没有 runtime 证据时只能更新为 `blocked` 或 `inference`。
4. 仅修改相应 `project.json.writeScope` 内文件；外部源、canonical commander mod 和
   地图任务脚本保持只读，除非有明确的阶段授权。
5. 新增或修改 launcher、Galaxy、adapter 后，`-NoLaunch` 只能做预检，最终验收必须经过
   实际游戏、listener/heartbeat 和 ScriptError gate。

## 风险与停止条件

| 风险 | 处置与停止条件 |
| --- | --- |
| SC2 未安装或 lease 被外部进程占用 | 不终止或接管外部 owner；记录 owner、端口和 run id，保持 `blocked` 并等待独立窗口 |
| 任务未达到终局 | 不把 step 上限、proxy reward、进程存活或首帧观测计为胜利；保留可重复的终局前 trace |
| 静态/模拟器与 runtime 混淆 | 在 result claim 中固定 evidence type；缺少 launcher/API/ScriptError 三项之一不得称 runtime pass |
| 当前工作树有未验证改动 | 先按改动范围运行测试和 `git diff --check`；阶段快照未刷新前不得提升状态 |
| 跨地图或跨指挥官泛化 | 只在每个目标的直接证据存在后扩展 contract；不从单图 P2 或单次 smoke 推广 |

## 计划完成定义

本计划不是任何模块的完成声明。它在以下条件同时满足后应被更新或归档：

1. 每个当前 `blocked` 或 `partial` 模块都有新的、可定位的 runtime 或明确 blocked 证据。
2. 每个 `passed`/`completed` 模块的开放运行时债务都已重新分类为已解决、可接受的维护风险，
   或新增独立维护阶段。
3. 所有阶段日志、结果和问题列表与 artifact 中的真实命令和 verdict 一致。
4. 工作树中影响这些模块的改动已通过相应回归，并以独立、可审计的提交保存。

## 2026-08-10 04:0x–04:2x 轮（Module 2 G4：抓到并修复 p95 长尾根因 VIBE-KERNEL-004）

上一轮把 G4 的 p95 红项诚实留成「未完全归因的开放缺陷」。本轮把它归因完了，而且是个真 bug。

### 1. 静态归因：watchdog 是 RPC 库上的第二个写者

`LibVibeKernel.galaxy` 的 VIBE-KERNEL-001 watchdog 每 `Wait(2.0, c_timeGame)` 无条件执行一次
`gf_WriteBankInt("index", "watchdog_last_seen_poll", …)`。而 `gf_WriteBankInt` 内部是
`BankSave(gv_bankHandle)` —— 把内核内存态**整份刷回 RPC 库 `GalaxyVibe.SC2Bank`**。

`VIBE_KERNEL_002` 铁律（2026-08-08 真机取证）写得清清楚楚：任何排在 `pending_request_id`
读取**之前**的 BankSave，都会用内核内存态覆盖磁盘，**永久抹掉** Host 的 `request/<id>` 与
`index/pending_request_id`。这条纪律当初只施加到了 **PollLoop 线程**上。watchdog 是同一个 Bank
上的**第二个写者**，与 PollLoop 的读写顺序毫无协调 —— 它一天也没遵守过这条铁律。

讽刺的是，`VIBE_KERNEL_005` 的注释里还专门点名 `watchdog_last_seen_poll` 是「Wait 之后由异步线程
写的、能正常落盘的键」，当时把它当**诊断线索**用，没意识到它同时是**抹除源**。

### 2. 定量预测与实测吻合

- 危险窗 = Host 落盘 → PollLoop 下一拍 `ReloadBank`，均匀分布 0~500ms；
- watchdog 周期 2000ms ⇒ 单请求碰撞率 ≈ 250 / 2000 = **12.5%**；
- 真机 n=100 实测 `over_2s_count` = **15**（15%）。

### 3. 为什么表现成「慢」而不是「丢」

Host 的 `_poll_response` 有 at-least-once 补发（`reassert_sec = 2.0`）：每 2 秒检查一次请求是否
还在所有候选 Bank 里，不在就用**同一 rid** 重发（内核靠 `lastPolledRequestId` 去重）。于是被抹掉的
请求都被救了回来，代价是延迟**按 ~2 秒量子阶梯化**：中位 684ms / p95 4904ms / max 7200ms
≈ 基线 + 1~3 次补发。

**补发一直在掩盖这个 bug，而不是在修它。** 这是本轮最值得记住的一条：一个「鲁棒性机制」把根因
藏了多久，就等于让根因多活了多久。

### 4. 修复 VIBE-KERNEL-004

watchdog 的心跳与重启计数改走**模型库** `gf_WriteModelBankInt`（VIBE_GEN_007 已做通道隔离，
其 `BankSave` 只刷 `GalaxyVibeModel.SC2Bank`，天然伤不到 RPC 库）。RPC 库的落盘时机仍由
`VIBE_KERNEL_005` 首帧 flush + 各 handler 的响应写入保证，不依赖 watchdog。
